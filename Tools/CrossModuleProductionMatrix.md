## Audit findings and boundaries

- The former ribbon label “MEP Openings” was ambiguous for a read-only clash-report command. It is now labelled “MEP Clash Review”; the tooltip and report both state the 50 mm-per-side assumption and that no opening is created. Structural framing, floors and walls are supported hosts; ducts, pipes and cable trays are supported MEP curves. Conduit, fittings, accessories, equipment, connector traversal and system-wide resolution remain unsupported/not claimed.
- Opening creation is intentionally `NOT_IMPLEMENTED`, not simulated. The read-only report is the shipped capability; no fake success or Revit mutation is reported.
- K-QS’s Revit scan is whole-document by default (explicitly named in the workbench), but its collector reads each host document once, sorts output deterministically and tracks source element IDs. Comparison import/export and local rule profiles do not mutate the Revit model. Quantity formulas and unsupported source handling are covered by domain acceptance.
- Architectural paths have explicit transaction ownership, postconditions and structured outcomes in their existing production services. Runtime fixtures exist for Room 3D and are registered/not executed.
- Rebar host coverage remains partial: circular-column creation has not been moved onto the solver-backed preview/fingerprint/parity lifecycle; Foundation side-tie settings are currently persisted but do not create bars; Wall Rebar has no active command or generator. Registered Foundation runtime preview/parity checks remain `NOT_EXECUTED` until run inside Revit.
- `FamilyManager` used to ignore transaction return states and symbol activation outcome. It now uses `TransactionBoundary` and checks activation after commit. `SlabStepForm` used to auto-load the default family during form construction; it now only selects an already-loaded default. Opening then canceling that form no longer changes the document; Browse/Load remains an explicit user action.
- Graphic Overdrive previously opened transactions inside its ViewModel. Mutation moved to `GraphicOverrideExecutionService`, which owns checked commit/rollback; the ViewModel now only forwards user selections and status.
- The repository-wide UI mutation audit also found transaction creation in legacy Rebar forms and three view-creation windows. Their transaction/group lifecycle now runs through `TransactionBoundary.Execute` / `ExecuteGroup`; a static gate scans production Forms, Windows and ViewModels and rejects direct transaction construction. The Rebar generators, preview fingerprints, rollback-only solver capture, pre-commit parity, and duplicate checks were retained; this is a transaction-owner change, not a geometry/planning change.
- Quick Structure previously ignored transaction lifecycle results, skipped unselected/missing beam or footing configuration while still showing “success,” and committed columns before later creation steps. It now validates all enabled inputs before mutation and submits one atomic service request. Only straight `Line` grids participate in the current XY intersection/planning algorithm; the UI reports how many curved grids were excluded. Floor creation is not an active operation (the older settings DTO's unused `CreateFloor` flag is not presented as implemented behavior).
- The canonical Stage 4 concepts remain distinct by responsibility: `WorkflowOutcome`/`WorkflowDiagnostic` describe shared execution semantics; domain-specific plans/results retain module data. No parallel generic result model or unproven helper consolidation was added.

No Phase 10 host-runtime scenario was executed. The code-side matrix and gates are evidence of source/build acceptance only, not proof of behavior in a live model.
